# AskOverlay - Architecture Decision Record

One file, all decisions. Each entry exists so the decision can be explained and defended, not just
followed. Newest decisions last. Dates are when the decision was recorded.

---

## ADR-0001: Single LLM seam via the Gemini Interactions API
Status: **Superseded in part by ADR-0007** (the single seam stays; the Interactions API and
server-side memory are replaced) - 2026-10-05

All LLM access goes through one module (`services/gemini_service.py`), using the Interactions API with
streaming and `previous_interaction_id` for server-side memory. Good for V1: memory for free, one place
to change LLM behaviour. Problems found later: interaction ids expire and likely belong to the API key
that created them, so a stale id or a switch from the demo key to a user's own key breaks the next turn,
and server-side memory means conversations live on Google's side, outside our control.

## ADR-0002: Raw function calling, not an agent framework
Status: **Superseded by ADR-0007** - 2026-10-05

With one tool (`read_screen`) and a fixed two-step flow, a framework was judged unjustified ("why
two?"). The owner has since decided to use LangChain/LangGraph; ADR-0007 records the reasons and the
evidence, and is honest that with a single tool the framework's value is modest.

## ADR-0003: Screen context via vision, not OCR; "Middle" capture strategy
Status: **Accepted - open question resolved** - 2026-10-09

- Vision, not OCR: UI screenshots (small antialiased fonts, text in controls, layout that carries
  meaning) defeat traditional OCR, and the task is screen understanding, not transcription.
- "Middle" strategy: the client captures one screenshot per send and attaches it; the backend declares a
  `read_screen` tool and the model decides whether to use it. If the model does not call the tool, the
  screenshot is discarded and non-screen questions cost nothing extra.
- Privacy: screenshot captured, sent, discarded if unused, never stored or logged. (See the free-tier
  caveat in ADR-0007.)

**Open question, now resolved.** Can the cheap model read UI screenshots, and can an image be returned
as a tool result? Live spike on 2026-10-09 (synthetic error-dialog screenshot, via LangChain
`ChatGoogleGenerativeAI`): `gemini-3.5-flash-lite` and `gemini-3.1-flash-lite` both read the error code
correctly from an image in a user message, and both answered correctly when the image was returned
*inside* a `ToolMessage`. `gemini-2.5-flash-lite` was not tested (Google now restricts 2.5 models to
existing users). Known limitation: combining Google's built-in tools (e.g. search) with custom
functions is not supported on the newest models through the Interactions API.

## ADR-0004: DB session lifecycle via `get_db`; client UI/dialogs split
Status: Accepted, committed - 2026-10-05

`get_db` FastAPI dependency owns session cleanup for ordinary routes; `ui.py` (widgets) and
`dialogs.py` (modal flows) separated so widgets do not depend on auth. Refined by ADR-0006:
`/chat` does not use `get_db`, because a request-scoped session would stay open for the whole stream.

## ADR-0005: BYOK plus a lifetime demo; no accounts, no payments
Status: Accepted - 2026-10-09

**Context.** V1 shipped Google OAuth, JWT sessions, a users table, and PayPal billing. The OAuth flow
lacked `state`/PKCE, stored an unused refresh token, and the deployed billing webhook could not work
over plain HTTP. The surface area was large relative to the value for a portfolio project.

**Decision.** Two access modes only: bring-your-own Gemini key (unlimited, zero cost to the developer)
or a demo of 10 requests per device, lifetime, on the backend's key. All accounts, JWTs, OAuth and
billing were deleted.

**Consequences.** Without identity, the demo cannot be protected per user (see ADR-0006). The backend's
key must live on a project with no billing attached. Conversation history is to be held by the client
(ADR-0007).

## ADR-0006: Demo abuse model - per-IP and global daily caps, atomic and all-or-nothing
Status: Accepted - 2026-10-09

**Context.** Device ids are generated by the client, so anyone can mint a fresh id per request. A
per-device cap is therefore a fairness limit, not a security control.

**Decision.** Three counters, checked together in one transaction: per device (lifetime, default 10),
per client IP (per UTC day, default 30), and global (per UTC day, default 300). Each is a single
`INSERT ... ON CONFLICT DO UPDATE ... WHERE count < limit`, so concurrent requests cannot overshoot; the
first cap already reached rolls the whole transaction back, so a rejected request consumes nothing. A
request that fails upstream before Gemini answers is refunded. `X-Forwarded-For` is ignored unless
`TRUST_FORWARDED_FOR` is set, and then only its last entry (added by our own proxy) is believed.

**Why not server-issued device tokens ("why two?").** With IP and global caps in place, signed tokens
add a signing secret and client changes for almost no extra protection: an attacker who can reach the
registration endpoint can mint tokens exactly as easily as ids.

**Residual risk, accepted.** A botnet with many IPs is bounded only by the global cap; users behind a
shared IP share the IP cap. All limits are configuration, not code.

## ADR-0007: LangGraph for the agent; the client holds conversation history
Status: **Proposed - spike and benchmark complete; default-model decision pending the owner** - 2026-10-09

**Context.** The owner wants LangChain/LangGraph. ADR-0001's server-side memory conflicts with removing
accounts and with privacy (chats stored outside our control), so history moves to the client: each
request carries the prior turns and the server is stateless.

**What the framework earns, honestly.** With history on the client there is no checkpointer, so the
persistence argument for LangGraph disappears. What remains: a graph with explicit nodes and a
conditional edge (`agent` -> `screen` tool node -> `agent`), a standard message/tool-call abstraction
across providers, and token streaming (`stream_mode="messages"`). With a single tool this is a small
graph; the stronger story arrives with a second tool (V1.2). If that is never built, a plain tool loop
would be equally correct and simpler. This is a deliberate trade, recorded so it is defensible.

**Spike results (2026-10-09, live, `langchain-google-genai` 4.4.0, `langgraph` 1.2.14, synthetic
screenshot).** Checks: plain invoke, token streaming, vision in a user message, tool call requested for a
screen question, no tool call for a non-screen question, image inside a ToolMessage, image in a following
user message (fallback), full LangGraph run with a streamed answer, and a stateless run with
client-supplied history.

Follow-up benchmark, same day: 12 interleaved rounds (so a slow period hits every model equally), two
workloads per model - a short text prompt and the product-critical "read the error code from this
screenshot" prompt - on the free-tier backend key. Times are seconds to first streamed token.

| Model | Text median / p90 | Vision median / p90 | Failures (of 24) | Vision accuracy |
|---|---|---|---|---|
| `gemini-3.1-flash-lite` | 1.5 / 8.6 | 1.7 / 3.9 | 0 | 12/12 |
| `gemini-3.5-flash-lite` | 7.1 / 10.9 | 8.4 / 16.3 | 0 | 12/12 |
| `gemini-3.5-flash` | 3.3 / 10.1 | 2.3 / 3.4 | 5 (HTTP 429) | 9/9 |
| `gemini-3.8-flash` | 20.5 / 65.9 | 4.4 / 6.0 | 13 (HTTP 429) | 5/5 |

Reading it: both lite models were 100% accurate and reliable on this key, but `3.5-flash-lite` was about
4-5x slower to first token than `3.1-flash-lite` (the earlier Interactions API timings of 11 s and 47 s
fit this pattern, so LangChain is not the cause, and `thinking_level` made no difference). The two
larger models are fast when they answer but hit free-tier quota limits, so they are unusable for a
backend-funded demo. Caveats: n = 12 per cell, one day, one free-tier key; latency on a free tier can
shift with load, and this run consumed part of that day's quota for the larger models.

**Recommendation.** Default to `gemini-3.1-flash-lite` for interactive use (the model is a config value,
`GEMINI_MODEL`, so this is a one-line change); keep `gemini-3.5-flash-lite` as an option. Re-measure on a
paid key before promising anything about production latency.

**Known risks.** `langchain-google-genai` pulls a much newer `google-genai` (2.29) than the backend pins
(2.10); the migration replaces the direct SDK dependency. Earlier reports of Gemini 3 thought-signature
errors on tool calls did not reproduce here, but the area is fast-moving: pin versions.

**Privacy caveat to verify.** Gemini API free-tier content may be used by Google to improve its
products; if so, screenshots sent through the free demo key contradict "never stored". Check the current
terms before making that claim, or send screenshots only on BYOK / a paid key.

**Next.** Owner picks the default model; then port `/chat` to the graph, with images stripped from
history before it is returned to the client.
